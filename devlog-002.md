## Tricky Parts
1. **MAUI 11 event-field shape (empirically probed, .NET 11.0.100 SDK + MAUI 11.0.10):** `Page` lifecycle event delegates are **private same-name fields declared on base `Page`** (`Appearing`, `Disappearing`, `NavigatedTo`, `NavigatingFrom`, `NavigatedFrom`) — there is no `Microsoft.Maui.Controls.Internals.NavigationEvents` in MAUI 11. And `Type.GetField` on the *runtime* type (`ContentPage`) does **not** return non-public fields of base types, so `PageEvents.GetEventDelegate` walks the base-type chain. `NucleusMvvmCore`'s auto-generated events (`AppResumed`/`AppStopped`/`ShellNavigated`/`ShellNavigating`) also land in **private same-name fields**, not `<X>k__BackingField` in this toolchain — `CoreEvents` reuses the same chain-walking helper. Both helpers are reflection, so this stays robust if the backing shape changes.
2. **xunit 2.9.3 API traps:** predicate overloads are `Assert.Contains/DoesNotContain(IEnumerable<T> collection, Predicate<T> predicate)` (collection *first*; no `IReadOnlyCollection` predicate overloads); there is **no** `Assert.Equal(T, T, string message)` overload. `xUnit2029` fires on `Assert.Empty(collection.Where(...))` — satisfied by `Assert.DoesNotContain(collection, predicate)` instead.
3. **Namespace/ambiguity traps in test code:** unqualified `NavigationMode` is ambiguous with `Microsoft.Maui.ApplicationModel.NavigationMode` (flowed global using) → explicit using-alias to `Mvvm.Nucleus.Maui.Compatibility.NavigationMode`. In `*.Services` test files, `Compatibility.X` binds to the *test* namespace `Mvvm.Nucleus.Maui.UnitTests.Compatibility` (CS0234) → using-aliases for `CompatibilityNavigationParameters`/`NavigationMode`. `NucleusMvvmCore.Shell` getter is `Shell?` → `Core.Shell!` at call sites. A field initializer referencing the harness base `Options` fails with CS0236 → lazy property instead.
4. **Debounce determinism:** `NavigationServiceStateReset` (reflection reset of static `_isNavigatingLastTriggeredUtc` + instance `_isNavigating`) before each debounce test — no sleeps, order-independent. The `IsNavigatingChanged` sequence in the in-progress test is exactly `[true]`.
5. **Async confirm-navigation:** the `IConfirmNavigationAsync` deny path suspends the Shell navigating handler mid-deferral — observed with a per-raise gate `TaskCompletionSource` (`ConfirmNavigationAsyncGate`): pre-release `Cancelled == false` with the direction already recorded, post-release `Cancelled == true` and the "Shell Navigation Canceled." Information log. `ShellNavigatingEventArgs`' public ctor + `GetDeferral()`/`Cancel()` all work in the bare host, so the plan's async-skip fallback was **not** needed.
6. **One self-inflicted failing test at the end:** `AfterNavigatedFrom_AppLifecycleEventsNoLongerRoute` asserted `OnNavigatedFrom` count on `ApplicationLifecycleViewModel`, which implements only `IApplicationLifecycleAware` (deliberately — it pins the `is TInterface` branch), so `OnNavigatedFrom` was never recorded. Removed the bad assertion; the unsubscribe intent stays pinned by `OnResume` staying at 1 and `OnSleep` at 0 after the From.

## Decisions Made
- **Per-test core:** every harness test constructs its own `NucleusMvvmCore`, calls `core.Initialize(sp)`, and registers `new Shell()`. This avoids `NavigationService` event-subscription cross-test leaks that a shared core would cause; parallelization is still disabled (process-wide `NucleusMvvmCore._current` + the debounce static).
- **Both plan-documented fallbacks RESOLVED in favor of keeping the tests** (no skips in the suite): the `ViewFactory` non-`Page`-with-`Page`-parent test works (`Element.Parent` is settable in the bare host), and the async confirm-navigation test works (deferral/`Cancel()` functional).
- Non-test helpers are `internal`/`private nested` in the test assembly to keep the xunit analyzer from picking up non-`[Fact]` public members.
